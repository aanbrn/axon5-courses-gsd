## Summary

`AGENTS.md` asks the agent not to edit files outside a GSD workflow. `hooks.workflow_guard` is off
by default and, when enabled, returns an advisory rather than a block for a top-level edit. Nothing
in the config schema's key list names an enforcement setting. The draft asks either for an opt-in
blocking mode or for the option to be labelled advisory-only.

The claim is what the schema lists, not a proof that no mechanism exists anywhere in the framework.

## Why an enhancement, not a feature request

`CONTRIBUTING.md` separates the two: an enhancement improves existing behaviour and "does not add
new commands, new workflows, or new concepts"; a feature adds something new and carries a higher
bar.

This draft improves the contract of one existing option. The blocking mode it asks for is an option
on `hooks.workflow_guard`, not a new command, workflow or concept; the second, cheaper ask is a
documentation correction. If a maintainer reads it as a new concept, the feature template is the
right home and this draft should be reshaped rather than filed as is.

## Draft

```text
### Pre-submission checklist

- [x] I have confirmed this improves existing behavior - it does not add a new command, workflow, or concept
- [x] I have searched existing issues and this enhancement has not already been proposed
- [x] I have read CONTRIBUTING.md and understand I must wait for `approved-enhancement` before writing any code
- [x] I can clearly describe the concrete benefit

### What existing feature or behavior does this improve?

`hooks.workflow_guard` - the opt-in guard intended to keep a change inside a GSD workflow.

### Current behavior

`AGENTS.md:434` tells the agent not to edit files outside a GSD workflow:

  "Do not make direct repo edits outside a GSD workflow unless the user explicitly asks to bypass it."

`hooks.workflow_guard` ships off by default (`bin/shared/config-defaults.manifest.json:82`) and is
documented at `workflows/settings.md:509` without a default. With it enabled, a top-level edit whose
path contains neither `.planning/` nor `.planning\` and matches none of the exempt patterns returns an
advisory and no block decision - the hook's header says so itself ("SOFT guard for edits - it advises,
not blocks", `hooks/gsd-workflow-guard.js:7-8`), and the payload carries `code: 'WORKFLOW_ADVISORY'`
with no `decision` field (`:365-372`).

The one hard block in that hook is `git add -f` on a branch matching `/^(worktree-)?agent-/`
(`:11`, `:112`); on an error caught by its outer handler the hook re-derives that blocking context and
blocks only when a Bash payload, an enabled guard and a determinable agent branch all hold (`:153-175`,
call at `:385`, block at `:386`).

Nothing in the config schema's key list names an enforcement setting: `validKeys` holds 126 bare
key-path strings with no per-key descriptions, exactly three start with `gates.`, and none contains
"enforc" (`bin/shared/config-schema.manifest.json:2`, `:4-129`). The three `gates.*` keys are read as
workflow step conditions (`workflows/execute-plan.md:84`), not as tool-layer guards.

### Proposed behavior

Either of these would close the gap; the second is the cheaper one.

1. An opt-in blocking mode for `hooks.workflow_guard`: when enabled, a write-like tool call outside
   `.planning/` and outside the exempt list is refused rather than advised.
2. Or, if blocking is deliberately out of scope, label the option advisory-only in its description and
   in `workflows/settings.md`, so a project does not enable it expecting a gate.

### Reason and benefit

**Why the current behavior is a problem:** the generated instruction states a rule that no setting
backs. A project that wants it enforced has to write its own rule as prompt text - which is what we
did - and prompt text is what an opt-in guard is supposed to make unnecessary. The name
`workflow_guard` also reads as an enforcement switch, so enabling it currently produces a false sense
of protection.

**Concrete benefit:** with option 1, the generated rule becomes checkable instead of aspirational, and
a project can choose between "advise" and "refuse" explicitly. With option 2, the documented contract
matches the behaviour - a smaller change that removes the trap, and the one I would accept first.

### Scope of changes

Option 2 is documentation only:

- the description of `hooks.workflow_guard` on the config schema surface
- the `workflows/settings.md` entry

Option 1 additionally touches:

- `hooks/gsd-workflow-guard.js` - emit a block decision when the new option is set
- the hook result path read by each runtime adapter
- tests covering both the advisory and the blocking mode

No new command and no new workflow.

### Breaking changes

None for existing installs: the option is new and off by default, and the current advisory path stays
the default behaviour. A project that turns the new mode on is opting into refused writes.

### Alternatives considered

- Leave it as is and document only (option 2 above) - cheapest, but the generated instruction stays
  unbacked.
- Make the guard blocking by default - changes behaviour for every project that already enabled it,
  and a tool-layer guard cannot know whether a call belongs to a running GSD command.
- Let each runtime adapter enforce its own rule - duplicates the decision in several places.

### Area affected

Runtime integration (hooks, statusline, settings)

### Additional context

Reproduction, against an installed tree (the hook sits beside `gsd-core/`, not inside it):

  H="$PWD/.opencode/hooks/gsd-workflow-guard.js"
  P=$(mktemp -d) && mkdir -p "$P/.planning" "$P/src"
  printf '{"hooks":{"workflow_guard":true}}' > "$P/.planning/config.json"
  echo "{\"tool_name\":\"Edit\",\"cwd\":\"$P\",\"tool_input\":{\"file_path\":\"$P/src/App.kt\"}}" \
    | node "$H"; echo " exit=$?"

Observed: one line of JSON, no decision field, exit=0, its additionalContext containing "Consider using
/gsd:fast ... or /gsd:quick ...". Exemption probes - a path under `.planning/`, a path ending in
AGENTS.md, and `session_type: "task"` - print nothing and exit 0.

The force-add block, both legs:

  H="$PWD/.opencode/hooks/gsd-workflow-guard.js"
  P=$(mktemp -d) && mkdir -p "$P/.planning"
  printf '{"hooks":{"workflow_guard":true}}' > "$P/.planning/config.json"
  git -C "$P" init -q -b agent-probe
  git -C "$P" -c user.email=probe@example.invalid -c user.name=probe commit -q --no-verify \
    --allow-empty -m probe
  echo "{\"tool_name\":\"Bash\",\"cwd\":\"$P\",\"tool_input\":{\"command\":\"git add -f x\"}}" | node "$H"; echo " exit=$?"
  git -C "$P" checkout -q -b feature-probe
  echo "{\"tool_name\":\"Bash\",\"cwd\":\"$P\",\"tool_input\":{\"command\":\"git add -f x\"}}" | node "$H"; echo " exit=$?"

Observed: on agent-probe, `{"decision":"block","code":"WORKTREE_AGENT_FORCE_ADD_FORBIDDEN",...}` on
stdout, the same reason on stderr, exit 2; on feature-probe, nothing, exit 0.

Both probes call the hook script directly; they do not run a runtime adapter end to end
(`plugins/gsd-core.js:756-758` invokes the hook for write-like tools and Bash; `:360-366` blocks only
on `decision: "block"` or exit 2; `:368-389` collects the advisory).

Related: #5036 concerns the wording of the generated instruction, not a blocking mode.

Filed from a personal hobby project that uses GSD for a learning exercise; the finding is about the
option's contract, not a production incident.
```
