## Summary

`AGENTS.md` states that a file edit must start from a GSD command. `hooks.workflow_guard` is the
only option that looks like it enforces that, and enabling it produces an advisory: the edit
proceeds. No configuration key in the schema claims enforcement, so the generated prohibition is
unbacked. This is a capability gap, not a bug — the report asks either for the gap to be closed or
for the option to say what it is.

## Reproduction

Run in an isolated directory, so the project's own configuration is untouched:

```bash
P=$(mktemp -d) && mkdir -p "$P/.planning"
printf '{"hooks":{"workflow_guard":true}}' > "$P/.planning/config.json"
echo "{\"tool_name\":\"Edit\",\"cwd\":\"$P\",\"tool_input\":{\"file_path\":\"$P/src/App.kt\"}}" \
  | node <gsd-core>/hooks/gsd-workflow-guard.js; echo "exit=$?"
```

Output on 1.20.1 — an advisory, exit 0, no `decision` field:

```
{"hookSpecificOutput":{"hookEventName":"PreToolUse","additionalContext":"⚠️ WORKFLOW ADVISORY: ...","code":"WORKFLOW_ADVISORY"}}exit=0
```

The same payload with `tool_name: "Bash"` and `command: "git add -f x"` prints nothing and exits 0,
because the force-add block is scoped to `agent-*` branches (C3).

## Draft

```text
Title: hooks.workflow_guard advises; no setting can require a GSD command

The generated instruction file tells the agent not to edit files outside a GSD workflow:

  "Do not make direct repo edits outside a GSD workflow unless the user explicitly asks to bypass it."
  (AGENTS.md, section "GSD Workflow Enforcement")

`hooks.workflow_guard` looks like the switch behind that rule, but enabling it only produces an
advisory. The hook states this in its own header:

  // This is a SOFT guard for edits - it advises, not blocks. The edit still proceeds.
  (hooks/gsd-workflow-guard.js:7)

Observed on 1.20.1 with `hooks.workflow_guard: true` and an `Edit` on a file outside `.planning/`:

  {"hookSpecificOutput":{"hookEventName":"PreToolUse","additionalContext":"... WORKFLOW ADVISORY ...",
   "code":"WORKFLOW_ADVISORY"}}
  exit=0

There is no `decision` field, so the OpenCode adapter treats it as an advisory and lets the edit
through (plugins/gsd-core.js:360-389). The hook's only hard block is `git add -f` on an `agent-*`
branch (gsd-workflow-guard.js:11), which a normal session never hits.

Two consequences:

- The instruction file states a prohibition that no setting backs. A project that wants it enforced
  writes its own rule as prompt text, which is what we did - and prompt text is what the workflow
  guard was supposed to make unnecessary.
- `hooks.workflow_guard` reads as an enforcement switch. If blocking is deliberately out of scope, the
  option's description and the `settings.md` entry should say "advisory only", so a project does not
  enable it expecting a gate.

A blocking mode is not obviously out of reach: whether a GSD command is active is already known to the
workflow. An opt-in mode that refuses a write outside `.planning/` when no command is active would make
the generated rule checkable instead of aspirational.

Drafted with assistance from an AI agent and reviewed before filing.
```

### Note on the first draft

An earlier version of this report claimed the guard is not registered on OpenCode at all,
generalising from the `opencode` capability descriptor's "no lifecycle hook registration"
(`bin/lib/capability-registry.cjs:2975`). The evidence pass disproved it: `plugins/gsd-core.js:753`
runs the hook. The claim was removed rather than reworded. The descriptor wording is accurate about
the installer and misleading about execution, which is why the report rests on C4-C5 instead.
